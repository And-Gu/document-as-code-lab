# Repository Guidance

## Sources and Scope

- Read `CONTRIBUTING.md` before editing tutorial content. Write project documentation in English.
- Keep `docs/` as the chapter source of truth. Astro in `site/` reads these files; do not duplicate or move them into the site.
- Preserve stable chapter IDs. Filename prefixes and `chapter_number` determine reading order.
- Keep existing user changes. Commit, push, or change GitHub settings only when requested.

## Keep Related Information Consistent

For a capability, publication, or workflow change, inspect the following files and update those affected. Do not edit every file mechanically.

- `README.md`: current status, available outputs, links, next milestone, and licensing.
- `site/README.md`: reproducible local commands, deployment, base path, and widget behavior.
- `docs/03-project-growth.md` and `data/features.json`: capability milestones and verification evidence. Mark complete only after its criterion is verified.
- `docs/10-publishing.md`: actual publishing tools, hosted status, and remaining output pipelines.
- `ROADMAP.md`: remaining work and decisions; do not leave completed choices described as undecided.
- `CONTRIBUTING.md` and `LICENSE.md`: conventions, license scope, and attribution when relevant.
- Supporting assets, tables, captions, links, and source lists when their inputs change.

Distinguish chapter draft status, approval, capability completion, and successful deployment. A passing build does not establish all four.

## Website and History

- Preserve the GitHub Pages base path `/document-as-code-lab/` in navigation, Markdown links, images, and scripts. Check both local and hosted paths.
- The chapter widget uses front matter and chapter-specific Git history collected at build time. Preserve full-history checkout in workflows; it is not a live API feed.
- Fixed charts under `assets/figures/` are historical teaching snapshots. Do not silently refresh their values or source revisions.
- Growth workflow artifacts do not automatically update chapter charts. Label working-tree previews separately from committed measurements.
- Chapter 3's interactive widget uses a separate JSON report regenerated by `site/`'s `predev` and `prebuild` hooks. Keep its measurement rules shared with the Python script, preserve Python setup in the website workflows, and restart the local server after new commits to refresh the report.
- Keep `site/dist/`, `site/node_modules/`, `.astro/`, and working reports under `build/` out of commits.
- When linking a new supporting source, check its material route and the explicit source-file selection in `site/src/lib/repository.ts`.

## Verification and Publication

- From `site/`, run `npm run check` and `npm run build`. Use `ASTRO_TELEMETRY_DISABLED=1` when sandboxed execution requires it.
- Run `.venv/bin/python -m unittest discover -s tests` from the root when changing measurement or processing behavior.
- For milestone changes, regenerate `scripts/measure_growth.py` reports with the appropriate Python environment; use `--include-working-tree` before committing.
- Check `git diff --check`, changed-file scope, internal links, and representative images and diagrams. Verify one title and one widget per chapter when changing their rendering.
- If Markdown rendering configuration changes but old HTML persists locally, use `npm exec astro sync -- --force` before rebuilding.
- Before an authorized push, synchronize with the remote without discarding changes. After publication, verify the deployment run and affected live pages. Report the exact commit and distinguish local checks from hosted verification.
- Search affected documentation for stale claims such as "deployment not configured", "pending publication", or "no license selected". Preserve genuinely historical explanations.
