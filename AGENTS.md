# Repository Guidance

## Sources and Scope

- Use the [project source map](reference/project-knowledge.md) to locate authoritative information and the [tutorial specification register](spec/tutorial/README.md) for design intent and dated decisions. Follow links relevant to the task; these files do not grant permissions or imply automatic context loading.

- Treat the lab as a self-contained tutorial. Use fictional data for exercises about business processes and keep those exercises separate from live business systems and operational approvals. Describe what readers can try or learn; explain the example’s scope only where it affects a reader’s action or interpretation. The Project Control Center reports on this repository’s actual activity.
- Read `CONTRIBUTING.md` before editing tutorial content. Write project documentation in English.
- Before rewriting prose, read the editorial rules in [CONTRIBUTING.md](CONTRIBUTING.md), the [shared vocabulary](GLOSSARY.md), and the approved narrative direction in the tutorial specification. Present representative before/after passages for owner approval before a major site-wide style change; preserve chapter objectives, source identifiers, and meaningful distinctions.
- Keep `docs/` as the chapter source of truth. Astro in `site/` reads these files; do not duplicate or move them into the site.
- Preserve stable chapter IDs. Filename prefixes and `chapter_number` determine reading order.
- Keep existing user changes. Commit, push, or change GitHub settings only when requested.
- For the data-enrichment insertion, existing published chapter source slugs (10-publishing and 11-beyond-github) are intentionally preserved for URL compatibility while their reader-facing chapter_number values advance to 11 and 12. This is a documented exception to the filename-prefix convention; never silently break those published routes.

Follow the [current audience and reader promise](spec/tutorial/02-DOCUMENT-AS-CODE-LAB-V1-SPECIFICATION.md#2-audiences-and-paths) and the [25 October decision](spec/tutorial/04-DESIGN-DECISIONS.md#25-october-2026-working-methods-direction). Preserve the twelve lesson chapters in reading order, followed by the standalone course summary. Preserve stable routes/anchors and a browser-first core without accounts or installation. Keep technical depth optional; do not imply automatic business-system integration. Exact copy and visual treatment remain subject to owner review.

## Keep Related Information Consistent

For a capability, publication, or workflow change, inspect the following files and update those affected. Do not edit every file mechanically.

- `README.md`: current status, available outputs, links, next milestone, and licensing.
- `site/README.md`: reproducible local commands, deployment, base path, and widget behavior.
- `docs/03-project-growth.md`: the history and traceability chapter with a dashboard link. `data/features.json`: capability milestones and verification evidence. Mark complete only after its criterion is verified.
- `docs/10-publishing.md` and `docs/11-beyond-github.md`: actual workflow behavior, hosted status, lab architecture, and remaining output pipelines.
- `ROADMAP.md`: remaining work and decisions; do not leave completed choices described as undecided.
- `CONTRIBUTING.md` and `LICENSE.md`: conventions, license scope, and attribution when relevant.
- Supporting assets, tables, captions, links, and source lists when their inputs change.

Distinguish chapter draft status, approval, capability completion, and successful deployment. A passing build does not establish all four.

## Website and History

- Preserve the GitHub Pages base path `/document-as-code-lab/` in navigation, Markdown links, images, and scripts. Check both local and hosted paths.
- The chapter widget uses front matter and chapter-specific Git history collected at build time. Preserve full-history checkout in workflows; it is not a live API feed.
- Fixed charts under `assets/figures/` are historical teaching snapshots. Do not silently refresh their values or source revisions.
- Growth workflow artifacts do not automatically update chapter charts. Label working-tree previews separately from committed measurements.
- The Project Control Center's growth widget uses a separate JSON report regenerated by `site/`'s `predev` and `prebuild` hooks. Keep its measurement rules shared with the Python script, preserve Python setup in the website workflows, and restart the local server after new commits to refresh the report.
- Keep `site/dist/`, `site/node_modules/`, `.astro/`, and working reports under `build/` out of commits.
- When linking a new supporting source, check its material route and the explicit source-file selection in `site/src/lib/repository.ts`.

## Verification and Publication

- Use the maintained workflow in [site/README.md](site/README.md#next-change-cycle). Select the runtime in `.node-version`, run the shared preflight, then the affected tests before the required broad gates. After a test-only correction, rerun that scenario first; an unchanged failure needs diagnosis rather than another full run.
- Read `npm --prefix site run delivery -- report` before delivery work. Start a record with a named owner when none is active; preserve an active owner and use an explicit reasoned handoff. Only that owner edits shared sources, builds, changes branches, commits, merges or publishes within the user's authorization. Assign browser test files/projects/targets to named workers with `delivery assign`; they execute the exact scope with `delivery test`. No second chat may silently take over or duplicate a completed scope. The record coordinates work; it does not grant permission or lock arbitrary Git commands.
- Full local browser runs require a clean checkout and a matching build revision before snapshotting or browser startup. Use `--preview` only with an explicit test file for working-tree UI checks. It cannot be used in CI or hosted verification. Source changes require rebuilding; after a commit or merge, allocate tasks for the new revision. Preserve the existing production and hosted identity assertions.
- Record local command phases with `delivery run`, manual/review/external-job intervals with `delivery begin/end`, and observed milestones with `delivery mark`. Leave unavailable request/authorization times unknown. Export `delivery report` into the observation in #37; do not add overlapping job durations or count this local JSON as another cross-session log. Browser runs record preflight, snapshot, browser, checkout and cleanup timing in their own evidence directory.
- For browser checks, use the npm runners. They allocate a port, snapshot the completed build and preserve each run's evidence separately. Builders still need exclusive ownership of `dist/` and generated data. Assert the selected UI state before measuring behavior and inspect the trace/state attachments on failure.
- The [delivery-loop log (#37)](https://github.com/And-Gu/document-as-code-lab/issues/37) is the cross-session experiment register. Read its current experiments and later observations when applying `retroperspective` or reviewing the delivery workflow. During authorized follow-up, append the change/PR, revisions, evidence, timings (unknown where unavailable), rework and result; update current experiment status without deleting history. Technical verification does not establish a measured speed improvement. Evaluate after three comparable cycles. Keep build/cache details in #30 and link them; do not create a second session log.
- Reuse selected local browser scenarios against the explicit hosted URL with `test:hosted -- --scenarios`. The revision guard must run before and after them. Keep the existing hosted smoke check; neither a local pass nor a successful HTTP response verifies a deployment.

- From `site/`, run `npm run check` and `npm run build`. Use `ASTRO_TELEMETRY_DISABLED=1` when sandboxed execution requires it.
- Run `.venv/bin/python -m unittest discover -s tests` from the root when changing measurement or processing behavior.
- Run `node scripts/test-budget.mjs` from `site/` when validating the website. For the optional PDF proof, follow `publishing/pdf/README.md`, run its focused tests, and inspect rendered pages. Record whether Mermaid CLI or a prepared SVG was used; do not claim the full PDF pipeline is verified from the prepared-SVG path alone.
- For milestone changes, regenerate `scripts/measure_growth.py` reports with the appropriate Python environment; use `--include-working-tree` before committing.
- Check `git diff --check`, changed-file scope, internal links, and representative images and diagrams. Verify one title and one widget per chapter when changing their rendering.
- Dynamic page routes opt in to Astro incremental static builds via `cacheKey` in `getStaticPaths()`. Keep these keys content-addressed and include every direct filesystem data dependency plus shared navigation; Astro separately checks imported code. Update `site/scripts/test-incremental-build.mjs` when routes or dependencies change, and run `npm run test:incremental`. PR caches are isolated by PR; the Pages action caches `site/node_modules/.astro` without caching `dist`. Scheduled snapshots and `build-information.json` must still update each build.
- If Markdown rendering configuration changes but old HTML persists locally, use `npm exec astro sync -- --force` for development and `npm run build:fresh` for a deliberately cache-invalidated production build. Ordinary `npm run build` preserves Astro's content and incremental page caches. Run `npm run test:scheduled-publish` when editing the lightweight scheduled Pages verifier.
- Before an authorized push, synchronize with the remote without discarding changes. After publication, verify the deployment run and affected live pages. Report the exact commit and distinguish local checks from hosted verification.
- Search affected documentation for stale claims such as "deployment not configured", "pending publication", or "no license selected". Preserve genuinely historical explanations.
